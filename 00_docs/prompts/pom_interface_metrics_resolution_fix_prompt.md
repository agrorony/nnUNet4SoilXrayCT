# Prompt — Fix resolution mismatch in POM interface metrics (Mishmar replicates)

> Paste into Claude Code, running inside the PSD/topology pipeline repo (same environment `pom_interface_metrics_prompt.md` ran in — it has real access to the network paths and the full-resolution volumes, unlike the Cowork device bridge). Fully autonomous — every decision point below has an explicit rule; log the decision and reasoning in the final report instead of pausing to ask.

## The problem, found after the fact

`pom_analysis_20260830_interface_metrics/` (from `pom_interface_metrics_prompt.md`) computed its "Mishmar mean ± SE, n=2" from two replicates at **different resolutions**: `mishmar_native` was loaded at its native **5.85 µm** (not downsampled), while `mishmar_sample2` was correctly loaded at its already-downsampled **~15 µm**. This is a resolution confound, not a real specimen difference — surface-area-based metrics (SSA, IAD, marching-cubes surface area) are directly sensitive to voxel size because finer voxels resolve more real surface micro-roughness. Confirmed quantitatively: `mishmar_native`'s SSA_total = 39.0 mm²/mm³ vs. `mishmar_sample2`'s 26.2 mm²/mm³ — a ~49% gap between two "replicates" of the same soil, the wrong kind of variation to be folding into an SE bar, and large enough to be driving part of the reported Bnei Re'em-vs-Mishmar IAD gap rather than reflecting it. This is the same class of resolution confound this project already has a name for and a precedent for handling (A2, for the pore-size-distribution comparison) — it just wasn't caught before this run shipped.

## The fix

**Do not re-derive a new downsample.** `pom_analysis_20260824_replicates/mishmar_label_downsample_1/summary_pom_metrics.json` already documents a resolution-matched version of `mishmar_native`: label-downsampled to 15.0 µm, shape 390³, pinned A1 noise-floor cutoff = 13 voxels, verified `pom_pore_contact_fraction` = 0.5988303585645836. Its `REUSED_FROM_ABLATION.md` note says the full `.nii.gz` itself was not duplicated there (to avoid copying multi-GB data) and instead lives at `pom_analysis_20260824_ablation/mishmar_label_downsample/` — locate it there. If it is genuinely missing (deleted, moved), regenerate it using the exact same label-downsample method already implemented for `mishmar_label_downsample_2` (reuse `pom_analysis_20260824_replicates/scripts/step_mishmar2_label_downsample.py` or the equivalent ablation-stage script — do not write a new downsampling method), applied to `mishmar_native`'s full-resolution segmentation, and verify it reproduces the pinned record (POM 1.614%, pore 26.108%, per `REUSED_FROM_ABLATION.md`) before proceeding — if it doesn't reproduce, stop and report the mismatch rather than continuing on an unverified volume.
